# MathSite 인수인계서

팀 저장소는 `bhy0426/math`다. 로컬 검토본의 변경 상태는 `git status`로 확인한다.

## 1. 먼저 알아둘 규칙

이 사이트는 학원이 회원을 승인하고 개별 강의를 허용하는 구조다. 구매·결제는 없다.

| 구분                     | 의미                                   |
| ------------------------ | -------------------------------------- |
| 강좌 courses             | 중등 수학 기초반 같은 수업 묶음        |
| 강의 lectures            | 강좌 안의 한 수업과 영상               |
| 역할 roles               | 관리자 작업을 할 수 있는 계정인지 구분 |
| 시청 권한 lecture_access | 학생·강의·시청 시작일·만료일           |
| 회원 항목 member_fields  | 아이디·닉네임·이메일의 수집·사용 여부  |

승인과 시청 허용은 다르다. active 학생이라도 강의 권한이 없으면 시청할 수 없다. 서버가 매 요청마다 역할·승인 상태·유효기간·강좌 소속·공개 상태를 검사한다. 관리자 버튼을 숨기는 것만으로 권한을 처리하지 않는다.

## 2. 읽는 순서

1. 이 문서로 실행 조건과 현재 상태를 확인한다.
2. [구조 지도와 코드 읽는 순서](code-map.md)에서 화면 하나와 API 요청 한 건을 따라간다.
3. [파일·함수 안내서](functions.md)에서 수정하려는 함수를 찾는다.
4. [API 목록](API.md)에서 요청·응답·권한을 확인한다.

두 `src`는 실행 장소가 다르다. `client/src`는 브라우저의 React, 루트 `src`는 Node.js 서버다. 화면 `/courses`와 데이터 요청 `/api/courses`도 다르다.

## 3. 파일 역할과 수정 원칙

```text
src/app.js                         전체 API 주소 연결·세션·오류 응답
src/models.js                      Sequelize 테이블·열·관계 매핑
src/database.js                    MySQL 연결과 연결 풀
src/modules/기능명/routes.js       요청 값 전달·HTTP 응답
src/modules/기능명/service.js      입력 검사·권한·처리·모델 호출
src/modules/user/member-fields.service.js  가입·회원 수정·응답의 공통 항목 규칙
src/modules/manager/member-settings.service.js  관리자 설정 저장·재로그인 보호
src/modules/mail                  발신자 등록·암호화 저장·공통 메일 전송
src/modules/auth/social.repository.js  공급자별 계정 연결의 공통 저장 함수
database/migrate.js                기존 DB를 모델 구조에 맞게 준비
database/migrate-social-accounts.js  구형 소셜 계정 백업·통합·검증
client/src/pages                   화면
client/src/shared                  공통 로그인 상태·입력·요청
tests                              Mocha와 합성 자료
```

예를 들어 회원정보를 수정할 때 `manager/routes.js`는 `service.editUser`를 호출하고 응답한다. 실제 처리 함수는 **같은 manager 폴더**의 `service.js`에 있다. 본인 수정과 공유할 처리는 user/service로 위임하고, 공통 항목 정책은 user/member-fields.service에 둔다. 관리자 설정 저장과 재로그인 보호는 manager/member-settings.service에서 조합한다.

강의도 courses 폴더 안의 `lectures.routes.js`와 `lectures.service.js`로 구분한다. 업로드는 `upload.js`, 변환 작업은 `video.js`, 시청 검사는 `access.js`다. 라우터 파일에 DB·파일·암호 계산 코드를 다시 넣지 않는다.

메일의 `routes.js`는 관리자 라우터의 `/mail`에 연결되어 `/api/manager/mail` 요청을 처리한다. 등록은 `mail/sender.service.js`, 암호화 보관은 `mail/sender.store.js`, SMTP와 공통 발송 함수는 `mail/transport.js`에 있다. 가입·비밀번호 초기화·학생 안내가 같은 전송 함수를 쓴다. 인증 서비스의 `publicConfiguration`은 공통 회원 정책과 메일 준비 상태를 합쳐 화면에 반환한다.

## 4. 실행과 새 PC 설정

Node.js 22.12 이상. 확인한 버전은 26.13.0이다.

```powershell
# 프로젝트 폴더에서 실행한다.
npm.cmd ci
# .env.example을 .env로 복사하고 실제 비공개 값을 입력한다.
npm.cmd run db:init
npm.cmd run dev
```

기본 주소: `http://127.0.0.1:3000/`. 일반 실행은 `npm.cmd start`, 종료는 터미널의 `Ctrl+C`다. 서버 재시작 시 메모리 세션이 사라져 다시 로그인한다.

새 PC는 MySQL의 **데이터베이스 자체와 계정**을 먼저 준비하고 `.env`에 입력한다. `db:init`은 그 DB 안의 테이블·열·역할을 준비하는 명령이다. 기존 회원이 있으면 최초 관리자 환경 변수로 계정을 덮어쓰지 않는다. 새 DB가 비어 있을 때만 `ADMIN_NICKNAME`, `ADMIN_USERNAME`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`로 관리자를 생성한다. 새 비밀번호는 8~128자다.

## 5. 공유 DB 적용 상태

개발 DB는 Filess.io 온라인 MySQL이다. 회원 항목·구글 연결 등 누락 테이블을 준비했다. 기존 중복 닉네임은 사용자 요청대로 보존하고 닉네임 고유 인덱스만 보류한다. 새로 입력하는 닉네임은 앱에서 중복 검사한다. DB 고유 제약은 기존 중복 정리 후 db:init을 실행하면 추가된다. 사이트의 가입·회원 수정은 공통 설정 행을 잠근 뒤 중복 검사와 저장을 수행한다. DB에서 직접 쓰는 작업까지 고유성을 보장하려면 기존 중복을 정리하고 인덱스를 적용해야 한다.

로컬 mathsite_test에는 매핑·제약을 적용해 검사했다. 기존 중복 닉네임과 누락된 member_fields 테이블을 함께 재현한 회귀 검사도 포함한다. 서버는 시작할 때 initialize를 호출해 필요한 구조를 준비한다.

구형 공유 DB에서는 `signup_codes.sent_at` 열에 `NOT NULL` 제약이 있어 첫 가입 코드를 저장할 때 오류가 났다. 발송 요청은 먼저 코드 행을 확보한 뒤 같은 트랜잭션에서 발송 시각을 기록한다. 마이그레이션은 기존 열이 `NOT NULL`인 경우에만 `NULL`을 허용하도록 변경한다. 이후 실제 가입 화면에서 첫 코드를 발송했고, 로컬 회귀 테스트로 기존 인증코드 행도 보존되는지 확인했다. [마이그레이션](../database/migrate.js)

회원 번호는 MySQL이 회원 행을 추가할 때 발급한다. 이메일 가입의 중복 확인과 코드 발송은 회원 번호를 발급하지 않는다. 코드를 확인한 뒤에 회원을 저장한다. 삽입 경쟁이나 트랜잭션 롤백으로 번호가 빌 수 있으며, 공유 DB에서 과거에 번호가 건너뛴 정확한 원인은 당시 기록이 필요하다. 기존 회원 번호는 권한·질문 등에서 참조한다.

## 6. Sequelize로 DB 수정하기

`models.js`가 테이블 매핑의 기준이다. 직접 SQL 파일과 query/execute 호출은 제거했다. `mysql2`는 Sequelize의 MySQL 드라이버로만 사용한다.

```javascript
// 조회: 조건과 반환 관계를 객체로 전달한다.
const user = await User.findByPk(userId);
// 저장: 매핑한 모델 속성으로 갱신한다.
await user.update({ nickname: nextNickname });
```

모델의 `User.nickname`은 기존 DB의 `name` 열에 `field: 'name'`으로 매핑된다. 화면과 API는 nickname을 쓴다. 기존 자료를 보존하기 위한 매핑이며 역할의 `Role.name`이나 강사 이름과는 다르다.

닉네임·아이디·이메일은 각각 고유하다. 꺼 둔 항목을 받지 않고 가입할 수 있도록 세 열은 NULL을 허용한다. NULL이 여러 개 있는 것은 중복 닉네임 사용과 다르다.

열을 추가할 때는 모델과 `database/migrate.js`의 QueryInterface 처리를 함께 수정한다. `sync()`는 없는 테이블·인덱스를 준비하지만 기존 열 변경을 모두 알아서 처리하지 않는다. `force:true`나 `alter:true`로 공유 DB를 재구성하지 않는다. 현재 마이그레이션은 열 존재 확인, 필요한 NULL 허용 변경, 중복 검사, 모델 동기화를 수행한다.

그룹 이름은 `student_groups`, 학생과 그룹의 연결은 `group_members`에 저장한다. 학생 안내 메일의 요청자·요청 식별 정보는 `mail_broadcasts`, 학생별 발송 상태는 `mail_broadcast_deliveries`에 저장한다. 전체 테이블과 관계는 [모델 파일](../src/models.js)에서 확인한다. signup_codes에는 가입 전 인증 정보가 임시로 들어간다. 과거 `site_settings` 테이블이 DB에 남아 있어도 조회하지 않는다. 자료 보존을 위해 자동 삭제하지 않았다.

### 소셜 계정 테이블 이관

2026-11-23 공유 DB에 적용했다. 기존 회원 9명과 카카오 연결 2건을 보존했고, 나머지 15개 테이블의 모든 행을 이관 전 백업과 대조했다. 기존 구글 연결 행은 없었다. 전체 Mocha 94개와 두 DB 연결을 사용하는 동시 이관 검사, 빌드·서식 검사, 재시작 후 공개 API 응답을 확인했다. 외부 카카오·구글의 새 인증 화면을 이용한 실계정 로그인은 이번 검사에 포함하지 않았다.

전체 DB 백업과 소셜 연결 원본은 이 PC의 `.local/backups`에 보관하며 검증 기록은 `social-migration-verification.json`이다. 공유 DB를 사용하는 다른 PC에도 이 수정본을 적용해야 한다.

현재 모델의 활성 테이블은 15개다. 회원·인증, 회원 그룹, 강좌·시청 권한, 게시판, 메일 발송으로 묶은 [데이터 관계도](code-map.md#데이터-관계)를 먼저 본다. `kakao_accounts`와 `google_accounts`의 연결 정보는 `social_accounts` 하나로 옮긴다.

| 열                 | 저장하는 정보                                                      |
| ------------------ | ------------------------------------------------------------------ |
| `provider`         | `kakao` 또는 `google`                                              |
| `app_key_hash`     | 연결할 앱·클라이언트의 식별 해시                                   |
| `provider_user_id` | 공급자가 발급한 계정 식별자                                        |
| `user_id`          | 기존 MathSite 회원 번호                                            |
| `user_scope`       | 회원별 중복 연결을 검사할 범위. 카카오는 앱 해시, 구글은 빈 문자열 |
| `created_at`       | 기존 계정을 연결한 시각                                            |

공급자·앱·외부 계정 조합은 하나의 회원에게 연결된다. 카카오는 앱마다 회원당 한 계정, 구글은 회원당 한 계정이라는 기존 제약을 `provider`, `user_scope`, `user_id`의 고유 인덱스로 유지한다.

이관할 때 공유 DB를 사용하는 구버전 서버를 종료하고 새 코드로 실행한다. `npm run db:init`과 서버 시작의 `initialize`가 다음 절차를 호출한다. [소셜 계정 이관 코드](../database/migrate-social-accounts.js)

1. 구형 테이블을 `_migration_kakao_accounts`, `_migration_google_accounts`로 바꾸어 복사 중 구버전 코드의 쓰기를 차단한다.
2. 테이블 구조와 연결 행을 `.local/backups/social-accounts-*.json`에 저장하고 저장 내용이 일치하는지 확인한다.
3. 트랜잭션 안에서 계정 식별자·회원 번호·연결 시각을 새 테이블에 복사한다. 이미 복사된 행은 모든 값이 일치하는지 확인하고, 다른 회원을 가리키면 이관을 중단한다.
4. 새 연결의 검증·커밋이 끝난 원본 임시 테이블을 정리한다. 중간에 중단되면 남아 있는 임시 테이블에서 다음 실행이 이어진다.

백업에는 계정 연결 정보가 들어 있으므로 서버의 비공개 `.local`에 보관한다. `.local`과 환경 설정은 Git·공유 ZIP 제외 대상이다. 원본 이름의 구형 테이블과 이관용 임시 테이블이 함께 발견되면 구버전 실행 여부를 확인한 뒤 다시 진행한다. 기존 `site_settings` 같은 다른 과거 테이블은 이 이관의 대상에 포함되지 않는다.

## 7. 회원 항목 스위치

**학원 관리 → 가입·로그인 설정**에서 저장한다.

| 설정       | 서버·화면에서의 동작                                                                         |
| ---------- | -------------------------------------------------------------------------------------------- |
| ON         | 가입에 입력 필요, 수정·회원 조회 응답에서 사용                                               |
| OFF        | 입력 화면 제거, API로 보낸 값도 거절, 응답에서 제외                                          |
| 이메일 ON  | 신규 가입은 이메일 중복 확인과 인증코드 입력으로 진행                                        |
| 이메일 OFF | 신규 가입은 설정된 소셜 계정으로 인증. 기존 아이디 로그인 지원. 관리자 초기화 메일 버튼 숨김 |
| 아이디 OFF | 아이디 로그인 불가, 이메일 로그인 사용                                                       |

아이디 또는 이메일 하나는 켜 두어 비밀번호 로그인을 유지한다. 선택 목록과 상단 메뉴는 켜 둔 항목 중 기존 값이 있는 닉네임 → 아이디 → 이메일 순서로 표시한다. 표시할 값이 모두 비어 있을 때만 `회원 번호 14`처럼 표시한다. 이 문구는 화면에서 만들며 DB의 닉네임을 변경하지 않는다. 비밀번호·내부 회원 번호·역할·승인 상태는 항목 설정과 별도로 관리한다.

공개 회원 설정 API는 켜 둔 항목만 반환한다. 관리자 설정 화면에서는 끈 항목도 다시 켤 수 있다. 로그인 실패 응답은 입력한 값이 등록됐는지 또는 어느 항목이 꺼졌는지 밝히지 않는다. OFF로 바꿔도 기존 DB 값을 지우지는 않는다. 다시 ON이면 기존 값이 보이고, OFF 기간에 가입해 값이 없는 회원은 내 정보·관리자 수정에서 입력한다. 닉네임·아이디·이메일은 다른 회원의 값과 겹칠 수 없다. 가입과 수정은 같은 검증 함수를 사용한다. 가입 화면에서는 활성 항목별로 중복 확인을 눌러야 하고, 값을 다시 입력하면 해당 확인은 해제된다.

설정 저장은 member_fields 세 행을 한 번에 갱신한다. 관리자 화면은 저장된 설정을 바로 반영하고 회원 목록을 다시 읽는다. 저장 요청이 거절되면 스위치는 마지막으로 읽은 설정으로 돌아간다. 저장에 성공한 뒤 회원 정보만 갱신하지 못한 경우에는 두 결과를 구분해 표시한다. 다른 브라우저는 화면 이동, 새로고침 또는 백그라운드 탭에 다시 돌아올 때 최신 설정을 읽는다.

관련 파일: `manager/member-fields.service.js`, `auth/account.js`, `user/service.js`, `client/src/shared/MemberFields.jsx`, `manager/MemberSettings.jsx`. 표시 순서는 [memberLabel.mjs](../client/src/shared/memberLabel.mjs)에서 고친다.

## 8. 회원가입·로그인·비밀번호 찾기

| 관리자 이메일 설정 | 학생이 회원가입에서 하는 일                                                | 계정이 생기는 시점                                      |
| ------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------- |
| 켬                 | 켜진 회원 항목과 비밀번호 입력 → 가입 인증코드 받기 → 받은 6자리 코드 입력 | 같은 브라우저에서 이메일과 코드를 검증하면 승인 대기    |
| 끔                 | 설정된 카카오·구글 중 하나로 인증 → 켜진 회원 항목 입력 → 가입 신청        | 서버가 인증한 소셜 계정을 학생에게 연결하면서 승인 대기 |

가입 화면은 [RegisterPage.jsx](../client/src/pages/RegisterPage.jsx), 이메일 가입은 [register.service.js](../src/modules/auth/register.service.js), 소셜 가입은 [social.service.js](../src/modules/auth/social.service.js)에서 수정한다. 학생을 승인하려면 관리자 → 회원 탭에서 해당 회원의 상태를 활성으로 바꾼다. 기존 회원은 내 정보에서 소셜 계정을 연결할 수 있다.

실제 회원가입 검증에서는 `/register`에서 코드를 요청하고 Gmail SMTP를 통해 수신한 6자리 코드를 같은 브라우저에 입력했다. 공유 DB에 `pending` 상태로 회원이 생성되었고 사용한 인증코드 행이 삭제된 것을 확인했다.

이메일 코드는 10분 동안 유효하다. 재발송은 60초 뒤에 가능하고 새 코드가 이전 코드를 대체한다. 같은 코드에 5번 틀리면 새 코드를 요청해야 한다. 가입 중 관리자가 이메일 스위치를 바꾸면 서버는 제출 시점의 정책을 적용한다.

카카오·구글도 우리 DB의 같은 역할·승인·정지 정책을 따른다. 신규 소셜 가입은 pending 학생이며 관리자가 승인해야 한다. 이메일이 같다는 이유로 기존 계정에 자동 연결하지 않는다. [공급자 설정](social-login.md)을 참고한다.

```text
기존 회원: 로그인 → 내 정보 → 카카오 또는 구글 연결
비밀번호 분실: 비밀번호 찾기 → 연결된 공급자로 인증
  → 서버에 5분 복구 세션 → 새 비밀번호 설정
  → 세션 버전 증가 → 기존 로그인 무효화 → 다시 로그인
```

공급자 ID·회원 ID·verified를 클라이언트가 임의로 보내도 복구 인증이 되지 않는다. 서버의 일회용 state, 연결 회원, active 상태, 세션 버전과 만료 시각을 검사한다. 구글은 PKCE도 사용한다. 계정 선택·카카오 인증은 공급자가 처리한다.

이메일 항목과 메일 발송 설정이 준비되면, 소셜 계정을 미리 연결하지 않은 회원은 관리자에게 초기화 메일을 요청할 수 있다. **아무 소셜 계정으로 인증하고 원하는 아이디의 비밀번호를 바꾸는 기능은 아니다.**

## 9. 비밀번호 저장·관리자 강제 초기화

`auth/password.js`의 PBKDF2-HMAC-SHA256은 비밀번호마다 임의 salt를 넣고 **600,000회** 반복 계산한다. 저장값에는 알고리즘·반복 횟수·salt·해시가 들어간다. 단순 해시를 몇 번 이어 붙이는 방식은 쓰지 않는다. [OWASP 권고](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)를 참고했다.

기존 scrypt 해시는 기존 비밀번호로 검증하고 성공한 로그인 때 새 저장 형식으로 갱신한다. 과거의 짧은 비밀번호도 이 이전 과정은 허용하지만, 새 가입·재설정은 8~128자만 받는다. 반복 횟수는 비밀번호 길이나 추측 용이성을 대신하지 않는다.

이메일 사용·발송 설정과 대상 회원 이메일이 준비되면 관리자 회원 탭에서 초기화 메일 발송 버튼으로 요청을 확인한다. 서버는 트랜잭션에서 기존 비밀번호를 임의 값으로 무효화하고 세션 버전을 증가시키며 30분짜리 토큰을 만든다. 토큰 원문은 메일에만 보내고 DB에는 SHA-256 해시를 저장한다. 메일 실패는 비밀번호·세션·토큰 변경을 롤백한다. 완료 토큰은 재사용할 수 없다.

첫 실행은 **발신 계정 미등록** 상태다. 관리자가 확인한 주소를 가입 인증, 비밀번호 초기화, 학생 안내 메일의 발신 계정으로 사용한다. `.env`에는 사이트 주소 `APP_URL`과 암호화에 사용하는 `SESSION_SECRET`을 설정한다. 예전 발신 계정을 자동으로 등록하거나 가져오는 과정은 없다.

1. **학원 관리 → 가입·로그인 설정**에서 이메일 사용을 켜고, **메일 관리**에서 현재 발신 주소를 확인한다.
2. 발신 계정의 제공자에서 2단계 인증을 켜고 MathSite 전용 앱 비밀번호를 발급한다. 네이버는 메일 환경설정에서 IMAP/SMTP 사용도 켠다. [Gmail 안내](https://support.google.com/accounts/answer/185833?hl=ko) · [네이버 안내](https://help.naver.com/service/30029/contents/21344)
3. 새 Gmail 또는 네이버 주소와 앱 비밀번호를 입력해 확인 메일을 요청한다. **새 주소가 보낸 메일을 그 주소에서 수신**한 뒤 요청한 관리자 세션에서 6자리 코드를 입력한다. 입력 기한은 10분, 재요청 간격은 1분이다.
4. 성공하면 가입·초기화·학생 안내 메일이 새 주소를 사용한다. 발신 정보는 서버의 `.local/mail-sender.json`에 암호화한다. 다른 PC는 별도 발신자를 등록할 수 있다. 같은 설정으로 서버를 이전하려면 이 파일과 기존 `SESSION_SECRET`을 비공개로 옮긴다. 대기 중 확인 요청은 재시작하면 새로 발급한다.
5. 등록 후 메일 관리 탭을 열거나 **연결 다시 확인**을 누르면 해당 계정으로 SMTP 로그인을 검사한다. 메일함 인증일과 최근 연결 확인 시각을 따로 표시한다. 인증 거절이면 제공자에서 2단계 인증과 앱 비밀번호를 확인하고, 일시적인 서버 연결 실패면 재검사한다. 새 주소로 교체할 때는 그 주소의 수신 코드를 확인한 뒤에 전환된다.

이메일 항목을 끄면 **메일 관리**와 **메일 발송** 탭이 숨겨진다. 관리자가 직접 발신 설정·수신자·발송·발송 결과 주소를 요청해도 404로 응답한다. 등록해 둔 발신 계정은 보존한다. 이메일 초기화 요청과 기존 메일 토큰의 비밀번호 변경 요청도 404이며 토큰·비밀번호·세션은 유지된다. 연결된 소셜 계정으로 하는 복구는 계속 사용할 수 있다. 이메일을 켠 상태에서 SMTP 미설정은 503, 실제 전송 실패는 502로 응답한다. Mocha는 테스트 전용 편지함과 모의 전송기를 사용한다.

### 반 그룹과 시청 권한

**학원 관리 → 회원 그룹**에서 반 이름을 입력하고 만들기·이름 수정·삭제를 할 수 있다. 활성 상태의 일반 회원을 배정한다. 한 학생이 여러 반에 속할 수 있다.

그룹을 하나 고르면 권한 변경 대상이 표시된다. 변경하지 않을 학생의 체크를 해제한 뒤 강좌와 강의, 부여 또는 회수를 선택한다. 부여 기한은 기본 30일이며 만료일을 지정할 수 있다. 서버는 적용 시점에 학생의 그룹 소속과 승인 상태를 다시 확인한다. 저장 결과는 회원별 시청 권한이다. 이후 반에 들어온 학생은 별도 부여가 필요하고, 그룹에서 제외되거나 그룹 자체가 삭제돼도 이전 시청 권한은 해당 만료일까지 유지된다.

### 학생 안내 메일 발송

1. **학원 관리 → 가입·로그인 설정**에서 이메일 사용을 켠 뒤 **메일 관리**에서 발신자를 등록한다.
2. **메일 발송**에서 그룹 하나를 고르면 유효한 이메일이 있는 활성 학생이 선택된다. 받지 않을 학생을 체크 해제한다. 그룹 밖에서 고르려면 **전체 학생 중 선택**을 사용한다.
3. 제목·본문을 작성하고 **발송 전 확인**에서 대상과 내용을 검토한 뒤 보낸다. 수신자는 학생별로 한 명씩 지정한다. 이메일 사용을 끄면 수신자를 조회하거나 학생 메일을 새로 보낼 수 없다.
4. 요청을 제출한 관리자가 학생별 결과를 확인한다. 접수 직후에는 처리 중이며, SMTP 서버가 메시지를 수락한 경우에만 발송 성공으로 집계한다. 학생의 받은편지함 도착·열람은 확인할 수 없다. 동일한 요청 번호로 다시 제출하면 기존 처리 결과를 반환한다. 처리 결과를 알 수 없는 전송은 자동 재발송하지 않는다.

## 10. 강좌 화면과 영상

학생과 원장님은 같은 강좌 주소를 사용한다. 원장님은 **강좌 → 편집 모드**에서 강좌와 영상을 등록·수정할 수 있다. 학생별 시청 허가는 **학원 관리 → 회원 관리**에서 해당 학생을 선택해 처리한다. [영상 모듈 연결 위치](code-map.md)

### 영상·Nginx

```text
관리자 업로드 → 관리자 검사·Multer·파일 서명 검사 → Lecture 저장
  → PROCESSING → FFmpeg H.264/AAC HLS 변환 → READY 또는 FAILED
학생 재생 → 현재 권한 검사 → 보호된 원본 또는 HLS 주소
각 재생 목록·영상 조각 → 다시 권한 검사 → Express 또는 Nginx 내부 전송
```

영상은 MySQL에 넣지 않는다. 원본은 `UPLOAD_DIR`, 변환 결과는 `HLS_DIR` 또는 `UPLOAD_DIR/hls`에 보관한다. DB는 경로 식별자·상태·권한을 저장한다. 온라인 DB를 공유해도 각 PC 영상 파일은 자동 공유되지 않는다.

이 PC 도구 경로:

```text
.local/tools/ffmpeg/ffmpeg-9.0.2-essentials_build/bin/ffmpeg.exe
.local/tools/nginx/nginx-1.30.6/nginx.exe
```

새 PC는 [FFmpeg](https://ffmpeg.org/download.html), [Nginx](https://nginx.org/en/download.html)를 별도로 준비하고 FFMPEG_PATH, NGINX_PATH, NGINX_PORT를 설정한다. 실행 파일은 공유 ZIP에 넣지 않는다.

```powershell
npm.cmd run media:check
npm.cmd run media:start
# http://127.0.0.1:8080/
npm.cmd run media:stop
```

템플릿은 `server/nginx.conf.template`, 생성 설정은 `.local/nginx`다. 보호 폴더는 internal이므로 직접 열 수 없다. 업로드 제한은 MP4/WebM·250MiB다. 변환은 한 프로세스 안에서 순서대로 처리한다. 서버를 시작하면 공유 DB의 `PROCESSING` 강의 중 이 서버에 원본이 있는 작업을 재개한다. 다른 PC에만 원본이 있는 작업은 상태를 유지한다. 수동 재변환도 로컬 원본을 확인한다. 재생 요청은 로컬 HLS 목록이 있으면 HLS, 원본만 있으면 원본 재생을 선택한다. 둘 다 없으면 404다.

교체 파일의 형식을 검사하고 변경을 DB에 저장한 후 기존 변환을 취소한다. 업로드 검증에서 잘못된 파일을 거절하면 기존 원본의 변환이 계속된다. 이 검사는 파일 헤더로 MP4·WebM을 구분한다. 파일 내용 전체의 재생 가능 여부는 FFmpeg 변환 결과에서 확인한다.

## 11. 검사와 연결 한도

```powershell
npm.cmd run db:start
npm.cmd test
npm.cmd run format:check
npm.cmd run db:stop
```

회원·강좌·게시판·소셜 인증·중복 확인·메일 교체·그룹·학생 안내 메일을 Mocha로 검사한다. 테스트는 로컬 `mathsite_test` 합성 자료를 재생성한다. `.env.local`의 DB_HOST는 localhost 또는 127.0.0.1이어야 하며 테스트가 DB_NAME을 mathsite_test로 강제한다. 테스트용 DB·권한·로컬 MySQL은 미리 준비한다. 새 PC에서는 자신의 MySQL 서비스로 켜도 된다. 이 PC의 db:start/stop은 전용 MySQL 경로와 `.local/mysql-admin.env`가 필요한 보조 도구다.

공유 DB 연결 장애 당시 서버 쪽에는 유휴 상태(`Sleep`)인 세션 5개가 열려 있었다. 해당 세션을 정리한 후 API가 다시 응답했고 실제 가입을 검증했다. 유휴 세션도 계정의 동시 접속 한도를 사용한다.

원격 DB의 연결 한도는 사람 수나 수정 횟수가 아니라 **열린 연결 수**다. Workbench 탭·SQL 편집기·각 PC의 Node 서버가 따로 사용할 수 있다. Sequelize 풀은 PC당 max=1, min=0이며 10초 유휴 후 정리 대상이 된다. DB의 동시 접속 한도에 도달하면 API가 503과 Retry-After 헤더를 보낸다. 시작 중 한도에 걸려도 화면 서버는 열린다. 이때 서버가 20초마다 한 번씩 DB 준비를 재시도하고, 성공하면 정상 API 처리를 시작한다. 재연결과 데이터 준비 중에는 각 단계가 표시된다. 화면의 조회 요청은 서버가 보낸 시간 뒤에 다시 시도하며, 등록·수정 요청은 자동 재전송하지 않는다. 사용하지 않는 본인의 Workbench 연결이나 개발 서버를 닫은 뒤 다시 시도한다. DB가 새 접속까지 거절하면, 소유자가 Filess의 Shared → 해당 DB → Overview → Quick Actions → Kill connections에서 기존 연결을 일괄 종료할 수 있다. 팀원 작업도 끊긴다. 종료 직후의 연결 수는 종료 전 사용자를 알려 주지 않는다.

## 12. 공유·미완료 범위

공유 ZIP은 코드·package-lock·공개 CA·시험용 영상·문서만 포함한다. `.env`, `.env.local`, `.local`, 실제 영상·DB 백업·node_modules·dist는 제외한다. DB 원본 백업은 회원정보와 인증 데이터를 포함하므로 개인 보관 위치에 두고 Git이나 팀 인수인계 ZIP에 포함하지 않는다. 비밀값은 비공개 전달 후 각 PC에서 입력한다.

외부 연결에서 남은 작업은 기존 중복 정리 후 닉네임 고유 인덱스 적용, Google OAuth 클라이언트 등록, 새 코드의 실제 카카오·구글 계정 인증 확인이다. 과거 카카오 실계정 연결 기록과 이번 공급자 응답 대체 검사는 구분한다. HTTPS 공개 배포·영구 세션 저장소·보고서 PDF·대면 회의 사진·제출은 팀의 후속 작업이다.

강좌·강의·Q&A·공지의 요청 파일은 권한 미들웨어를 연결하고 HTTP 요청·응답을 처리한다. 입력 검증과 데이터 변경은 해당 모듈의 서비스에 모여 있다. 그룹의 소속 학생 판정을 시청 권한과 메일 발송이 공유하므로, 학생 선정 기준을 바꾸면 두 기능의 테스트를 함께 실행한다. 가입·프로필·관리자 수정도 동일한 회원 항목 규칙을 따르므로 필드를 추가할 때 세 화면과 로그인 테스트를 함께 본다.

관리자 화면에서 회원을 승인하거나 회원의 역할을 배정할 때는 [회원 서비스](../src/modules/manager/service.js)를, 역할 자체를 추가하거나 이름을 바꿀 때는 [역할 서비스](../src/modules/manager/roles.service.js)를 연다. 한 학생과 반 전체에 시청 권한을 줄 때는 같은 [기간 검사](../src/modules/courses/access.js)의 `accessPeriod`와 [권한 저장 함수](../src/modules/manager/lecture-access.service.js)의 `saveLectureGrants`를 사용한다. [Sequelize 모델](../src/models.js)의 열 이름이나 관계를 바꿀 때는 해당 모델의 서비스와 [기존 DB 마이그레이션](../database/migrate.js)도 함께 살펴본다.

아이디 또는 이메일 로그인을 끄는 설정은 남은 항목에 값이 있거나 현재 앱의 소셜 계정이 연결된 활성 관리자가 있는지 확인한다. 모두 재로그인할 수 없는 설정은 409로 거절한다. 이 경우 설정을 유지한 채 관리자 프로필에 남겨 둘 아이디·이메일을 먼저 등록하거나 사용할 소셜 계정을 연결한다.

같은 브라우저의 다른 탭에는 설정 변경을 알리고, 다른 PC의 창은 다시 선택할 때 서버 설정을 읽는다. 계정이나 관리자 권한이 바뀌면 열어 둔 Q&A 상세와 같은 화면 상태를 비운다. 이 동작은 [로그인·설정 상태](../client/src/shared/auth.jsx)와 [공통 화면](../client/src/shared/components.jsx)에서 확인할 수 있다. [회원 항목 테스트](../tests/social.test.js)는 아이디·닉네임·이메일의 여섯 가지 유효한 조합에서 내 정보·회원 명단·중복 확인·메일 수신자에 반환되는 필드를 비교한다.

시연할 영상은 같은 저장소를 사용하는 서버에서 업로드·재생한다. 시연 전에 이메일·소셜 중 사용할 가입 경로를 실제 계정으로 한 차례 확인한다. 보고서에 넣을 API 수와 각 라우터의 핵심 테스트, PDF와 대면회의 사진 준비 항목은 [기말 평가 점검표](requirements-status.md)에 모았다.
